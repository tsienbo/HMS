# 智慧医院预约挂号系统

一个可直接运行的医院挂号系统，包含**患者端**预约挂号全流程与**管理端**号源调度后台。

前端为原生 JS 单页应用（无构建步骤、无框架、无 CDN），后端为 **Node + Express + PostgreSQL**。数据全部持久化在 PostgreSQL 中，支持并发挂号且不会超卖。

> **代码风格**：2026-10-13 做过一次「**初学风化**」重写 —— 全部前后端代码改成了**初学者能一行一行读懂的写法**：
> 页面骨架写在 `index.html` 里、`onclick` 直接写在标签上、状态就是几个全局变量、提示用 `alert` / `confirm`。
> **前后端各只有一个 JS 文件**：前端 `js/app.js`（分十二节）、后端 `server/app.js`（分九节）。
> 写前端时还有两条硬规矩：**不用 `.map` / `.filter` / `.find` / `.reduce`，一律写 `for` 循环**；
> **不写嵌套的三元表达式，要判断就写 `if / else`**。
> 2026-10-14 又做了一次「** HTML 归 HTML**」：原先在 JS 里用字符串拼出来的**静态结构**
> （管理端两个子页签的筛选栏、表格表头、加载中 / 空数据提示）全部搬回 `index.html`，
> JS 只负责往写好的容器里填数据和切显隐 —— 想改页面长什么样，改 HTML 就行，不用去翻 JS。
> 重写前的「进阶版」完整保留在 `legacy/2026-10-13-初学风化前/`，可对照阅读。
> 详见下方《关于「初学风化」这次重写》《关于「为什么前端只有一个文件」》《关于「为什么后端只有一个文件」》。

## 快速开始

### 1. 前置条件

- **Node.js** ≥ 18
- **PostgreSQL** 已安装并启动（本项目在 PostgreSQL 18 上开发验证）

### 2. 安装与初始化

```bash
cd hospital-registration

# 安装依赖
npm install

# 建库、建表、灌入示例数据
npm run db:init
```

数据库连接参数**直接写在 `server/app.js` 开头的 `DB_CONFIG` 里**，没有 `.env`、没有配置文件。
本机 PostgreSQL 密码不是 `123456` 的话，改那一处就行：

```js
// server/app.js
const DB_CONFIG = {
  host: '127.0.0.1',
  port: 5432,
  user: 'postgres',
  password: '123456',   // ← 改成你本机的 PostgreSQL 密码
};
```

### 3. 启动

```bash
npm start
# 浏览器打开 http://127.0.0.1:3000/
```

Windows 下也可以直接双击 **`启动.bat`**，它会启动服务并自动打开浏览器。

### 4. 管理后台账号

`npm run db:init` 会创建一个后台账号，密码用 **scrypt** 派生后存库（明文不落库）：

| 用户名 | 密码 | 说明 |
|--------|------|------|
| `admin` | `admin123` | 系统管理员：挂号记录、排班号源、调号源、停诊、退号 |

> 早期版本还有一个 `triage`（门诊值班员）只读账号，配套 `users.role` 角色列与
> `requireRole` 中间件 —— 已随 2026-10-12 的简化一起删除，只留一个管理员账号。
>
> ⚠️ **正式部署请立即修改默认密码**：改 `server/app.js` 里的 `USERS` 常量，再 `npm run db:reset`。
> 患者端预约挂号**不需要登录**。

## 数据库连接配置

连接参数写死在 `server/app.js` 里，建表和启动复用同一份，**没有 `.env`、没有 dotenv**：

| 参数 | 值 | 写在哪 |
|------|-----|--------|
| 主机 / 端口 / 用户 / 密码 | `127.0.0.1` / `5432` / `postgres` / `123456` | `server/app.js` → `DB_CONFIG` |
| 库名 | `hospital_registration` | `server/app.js` → `DB_NAME`（库不存在会自动创建） |
| 服务端口 | `3000` | `server/app.js` → `PORT` |
| 会话有效期 | 12 小时 | `server/app.js` → `SESSION_TTL_HOURS` |

另外还有两个可选环境变量，**平时完全不用管**，不写就是默认值：

| 变量 | 作用 |
|------|------|
| `PGDATABASE` | 临时换一个库名，不动 `server/app.js` 也能连别的库 |
| `PORT` | 临时换一个端口，3000 被占了就换一个 |

```bash
# 例子：连另一个库、跑在 3100
PGDATABASE=hms_test PORT=3100 node server/app.js
```

> 不带这两个变量时，行为和不写一样。
> 想要 100% 写死，把这两行的 `process.env.xxx ||` 去掉即可。

## npm 脚本

| 命令 | 作用 |
|------|------|
| `npm start` | 启动服务 |
| `npm run dev` | 启动服务（`--watch` 自动重启） |
| `npm run db:init` | 建库建表 + 灌入示例数据。**幂等且安全**：先探测表结构与数据，缺什么补什么，**不会删除已有数据** |
| `npm run db:reset` | **清空重建**（`--force`），会删掉所有表和挂号记录，慎用 |

> `db:init` 与 `db:reset` 的区别很重要：日常只想「补建缺失的表」用 `db:init`；
> 只有确定要丢弃全部数据时才用 `db:reset`。

四个脚本其实是同一个文件的不同参数 —— 命令行参数决定 `server/app.js` 干什么：

```bash
node server/app.js           # 不带参数 → 启动服务
node server/app.js --init    # 初始化（幂等）        ← 对应 npm run db:init
node server/app.js --force   # 删表重建（会清空）    ← 对应 npm run db:reset
```

## 认证与鉴权

管理端不是"所有人都能进"的：

| 层次 | 措施 |
|------|------|
| **口令存储** | Node 内置 `crypto.scrypt`（N=16384/r=8/p=1）派生，每条独立随机盐，格式 `scrypt$<salt>$<hash>`；校验用 `timingSafeEqual` 定长比较，避免时序侧信道 |
| **会话** | 登录签发 256 bit 随机令牌，落库到 `user_sessions`（含过期时间）。**不用 JWT** —— 令牌落库才能真的注销、踢下线、审计登录历史 |
| **接口保护** | 写操作在每个接口开头调一次 `getLoginUser(req)`，取不到用户就直接 401 —— 没有中间件，一眼能看出哪些接口要登录 |
| **错误提示** | 登录失败统一回「用户名或密码错误」，不区分账号不存在与密码错误 |
| **越权防护** | 匿名查询挂号列表必须带 `idCard`，且返回的证件号做脱敏；写操作需要令牌。~~退号需提供身份证号确认归属~~ 已移除 |

受保护的接口（**全部只需登录，不再区分角色** —— 只有一个管理员账号）：

```
GET    /api/auth/me                        当前登录用户        需登录
POST   /api/auth/logout                    注销                需登录
PATCH  /api/schedules/:sid/quota           调整号源            需登录
POST   /api/schedules/:sid/toggle          停诊 / 恢复出诊      需登录
```

公开接口：科室 / 医生 / 排班查询、挂号、退号。
退号**不强制登录** —— 匿名也能退自己的号；带了令牌时服务端把操作人写进 `close_note`。
`GET /api/appointments` 匿名调用**必须带 `idCard`**（否则 401），带令牌时返回全部记录。

**退号留痕** —— 管理端退号时会把操作人写进 `appointments.close_note`（形如「管理端退号（admin）」），配合 `cancelled_at` 时间戳，足以回答「这条号是谁什么时候退的」。审计表与触发器已删除，当前状态以 `appointments.status` 为准。

## 关于「为什么不建 hospitals 表」

本系统面向**某一家医院**的挂号业务，医院是部署期常量，不存在第二家医院，因此：

- 不建 `hospitals` 表，医院名称 / 等级 / 地址放在前端常量 `js/app.js` 的 `HOSPITAL` 里，换医院只改一处
- `departments` / `schedules` / `appointments` 上都没有 `hospital_id` 外键

如果硬留这张表，`hospital_id` 三列会恒为同一个值，`UNIQUE (hospital_id, name)` 也会退化成 `UNIQUE (name)` —— 这是典型的**伪 1:N 冗余**：多了一张表、三个外键、一个索引，却没有换来任何约束能力。

## 关于「号源为什么不按 30 分钟拆分」

早期版本把号源拆成 S1–S12 十二个 30 分钟格子，存在 `schedule_slots` 表里。后来删掉了，理由：

- **患者挂号时选的最小单位本来就是「上午 / 下午」**，再细的格子只是系统内部的东西，患者根本没选过；
- **具体几点几分就诊，由到院签到后的现场叫号决定**，与预约时选的格子并不一一对应 —— 硬把两者绑在一起是伪精确；
- **代价却是真实的**：多一张表、多一层 JOIN、多一份要同步的状态。最典型的是有人退号，
  如果时间按格子推，后面所有人的就诊时间都得跟着往前挪。

合并之后：`schedules` 一行 = 某医生某天某个半天，号源量就是这一行的
`quota_total` / `quota_booked` 两列；挂号与退号只在这两个数字上加减。
`appointments` 也去掉了 `slot_id` / `slot_label`，只保留 `period`（上午 / 下午）这一列快照。

代价是"取号序号"的语义变了：它现在是**该半天的第几个号**（到院后按它叫号的顺序），
而不是"某个 30 分钟格子里的第几个"。退号时后续序号前移的规则保持不变。

> 迁移脚本 `server/migrations/` 目录已在 2026-10-12 的后端瘦身中整体删除 ——
> `schema.sql` 就是最终形态，不需要再跑迁移；重跑旧迁移反而会把已经删掉的列加回来。

## 关于「哪些字段不该进数据库」

判据只有一条：**这一列会不会出现在 `WHERE` / 约束 / 索引 / 统计里？**

不会、而且它只服务于"看起来长什么样"，那它就属于展示层。本系统按这条原则处理了四样东西：

| 内容 | 原表 / 原列 | 现在的去向 |
|------|-------------|-----------|
| 医院名称、等级、地址 | ~~`hospitals` 表~~ | `js/app.js` 的 `HOSPITAL` |
| 科室图标（emoji） | ~~`departments.icon`~~ | `js/app.js` 的 `DEPT_ICONS`（按科室编号取） |
| 医生擅长方向 | ~~`doctors.good_at`~~ | `js/app.js` 的 `DOCTOR_INTRO`（按医生编号取，页面作为简介展示） |
| 医生评分 / 接诊量 | ~~`doctors.rating` / `doctors.cases`~~ | 整列删除，界面也不再显示 |

理由分别是：

- **医院**：只服务一家医院，`hospital_id` 会恒为同一个值，`UNIQUE (hospital_id, name)` 退化成 `UNIQUE (name)` —— 典型的伪 1:N 冗余。
- **科室图标**：图标是"怎么画"。换一套图标不该需要改库、跑迁移，而它也确实不参与任何查询。
- **医生擅长方向**：本系统**没有「按擅长方向搜索 / 筛选」的功能**，这段文字永远不会出现在 `WHERE` 里，它只是一段给患者看的介绍文案。
- **医生评分 / 接诊量**：它们只被医生卡片拿来显示"⭐ 4.9 / 接诊 12800 次"。全项目搜下来，只出现在建表、种子数据、`INSERT`、mapper 和那两行卡片文字里 —— 没有一处是查询条件或排序依据。管理端的"医生排行"排的是挂号笔数（`ORDER BY COUNT(*) DESC`），医生列表排的是职称档位，两条都和它们无关。既然用户明确不要，就整列删掉，界面也一并去掉。

**对照反例**最能说明分界线在哪：`doctors.title`（职称）看起来同样只是个给人看的标签，但它**真的进了 `ORDER BY`** —— 医生列表按「主任医师 → 副主任医师 → 主治医师」排，而且它还是 `ck_doctor_title` / `ck_doctor_fee_tier` 两条约束的判定依据，所以它**必须留在库里**。

判据不是"是不是给人看的"，而是"有没有东西真的去查它"。

改前面三样东西时，只需要改 `js/app.js`，不用碰数据库、不用跑迁移。

## 关于「为什么库里只有表、约束和索引」

判据也只有一条：**这个对象有没有人真的调用？**

本项目刻意**不建视图、不建独立函数、不建存储过程、不建触发器**。整个库里只有 6 张表 + 完整性约束 + 索引。这不是"没做"，是查过调用方之后主动删掉的：

| 对象 | 类型 | 谁在用 | 处置 |
|------|------|--------|------|
| `v_schedule_usage` | 视图 | **全项目零调用方** | 删除 |
| `v_doctor_workload` | 视图 | `GET /api/stats/doctor-workload` | 删除（该接口随后也一并下线） |
| `fn_doctor_remain` | 函数 | **全项目零调用方** | 删除 |
| `fn_dept_daily_stats` | 函数 | `GET /api/stats/daily` | 删除（该接口随后也一并下线） |
| `sp_archive_past_appointments` | 存储过程 | **零调用方**（管理端从没接过按钮） | 删除 |
| `appointment_audit` | 审计表 | 只有「操作日志」页在读 | 删除 |
| `trg_appointment_audit` | 触发器 | 审计留痕 + 挂号费快照守卫 | 删除 |

前五个没人调用 —— 视图/函数只是把一条 SQL 换个地方放，却多出一份要跟着表结构一起维护、还可能改漏的负担。`v_doctor_workload` 与 `fn_dept_daily_stats` 当时虽然还有人调用，但查询只服务那一个接口，先把 SQL 内联进了统计路由；后来整个统计模块也在 2026-10-12 的简化中删掉了（见《为什么管理端只剩两个页签》）。

**审计表与触发器**功能本身没写错，但它服务的是一个「以后才做」的需求：追溯「谁在什么时候把哪条挂号从什么状态改成了什么状态」。当前阶段不关心这个 —— 只关心**这条挂号单此刻是什么状态**，而 `appointments.status` 这一列已经说清楚了。既然没有查询去读审计表、「操作日志」页也一并下线，它就同样落回上面那条判据。

> ⚠️ **触发器丢掉的那道守卫，后来用「约束」补回来了（不是触发器）**：那个触发器原先还兼任「拒绝 `UPDATE appointments.fee`」的守卫（挂号费是下单那一刻的价格快照，改了会让 `SUM(fee)` 收入统计失真）。删掉触发器时，这道数据库级守卫也一并没了。**2026-10-13 起改用外键 `fk_appt_doctor_fee`** —— 它要求挂号单上的 `(doctor_id, fee)` 必须能在 `doctors` 表里找到同一对，所以 `UPDATE appointments SET fee = 1` 会因「价目表里不存在 DR01 + 1 元这一档」而被数据库直接拒绝（SQLSTATE `23503`）。效果与触发器相同，但它是声明式约束，不用写 PL/pgSQL，也没有触发器的执行开销。

**完整性设计依然扎实，而且全部落在约束上**（约束才是无法绕过的）：6 个主键（实体完整性）、8 个外键（参照完整性，含把「医生 + 挂号费」绑成一个整体的 `fk_appt_doctor_fee`）、15 个 `CHECK`（域完整性 + 跨列业务规则，如 `ck_doctor_fee_tier` 价格按职称分档、`ck_schedule_not_oversold` 防超卖）、4 个 `UNIQUE` 约束。

> 原本还有 1 个部分唯一索引 `uq_appt_same_doctor`（同一人同日同医生只能有一个有效号）与配套的普通索引 `idx_appt_conflict`。两者在 2026-10-12 按「暂时不搞防黄牛机制」删除，**索引 21 → 19，库里不再有任何部分索引**。（2026-10-13 新增 `uq_doctor_id_fee` 后又 +1，现为 20 个。）

## 关于「为什么挂号接口只有基本功能」

判断标准只有一条：**这一步不做，挂号还能不能成？**

挂号真正核心的只有四件事：

1. 校验就诊人信息（姓名 / 身份证 / 手机号）
2. **用一条自带条件的 `UPDATE` 扣号源**（详见《并发安全》一节）
3. 挂号费由**数据库自己**确定 —— 写单的 `INSERT` 语句里 `fee` 一列填的是标量子查询 `(SELECT fee FROM doctors WHERE id = $4)`，请求体传什么价格都不参与运算
4. 退号：把号源加回去 + 置为 `cancelled`

其余都属于「防黄牛」加码，与挂号主流程无关，已按「暂时不搞防黄牛机制」的要求**全部移除**：

| 移除项 | 原来做什么 | 现在 |
|--------|-----------|------|

### 事务删了，怎么保证不超卖？

老写法是「开事务 → `SELECT … FOR UPDATE` 锁住排班行 → 判断 → 扣 1 → 写单」。
新写法只有一条 SQL：

```sql
UPDATE schedules SET quota_booked = quota_booked + 1
 WHERE id = $1 AND quota_booked < quota_total
RETURNING quota_booked
```

`WHERE` 里的条件和 `SET` 里的加一**是同一条语句的一部分**，PostgreSQL 执行时会给那一行加锁，
所以「判断」和「扣减」之间不存在任何空隙 —— 20 个人同时抢最后 1 个号，只有 1 个人能更新成功。

- `rowCount = 1` → 抢到了，`RETURNING` 回来的 `quota_booked` 正好当**取号序号**用
- `rowCount = 0` → 号满了，直接回 409「该时段号源已挂完」

**没有事务就必须自己补偿**，所以另外补了两处：

- 号扣成功了、但紧接着写 `appointments` 失败 → `UPDATE schedules SET quota_booked = quota_booked - 1`，把号还回去；
- 退号路由的 `UPDATE … WHERE` 里重复写上 `AND status = 'active'` —— 重复退号时第二次会命中 0 行，直接回 409，**不会把号源退两次**。

代价是 `ck_schedule_not_oversold` 从「最后一道保险」变成了**数据库层唯一的兜底**。

## 核心业务规则

系统不是"能点就行"的空壳，以下规则均已在数据库与代码层实现：

- **号源原子扣减** —— 挂号成功即扣减，退号立即回滚
- **号源超卖保护** —— 半天约满时拒绝挂号；管理端调整号源总数不得小于已预约数（接口与 `CHECK` 双层拦截）
- **挂号费由数据库定价** —— 写单的 `INSERT` 里 `fee` 一列填的是子查询 `(SELECT fee FROM doctors WHERE id = $4)`，请求体传值不参与运算；外键 `fk_appt_doctor_fee` 再兜一道底，一元挂号单在任何写入路径下都会被拒
- **序号重排** —— 退号后，该半天后续患者的取号序号自动前移，不出现空号
- **停诊联动退号** —— 医生停诊时，该排班下所有有效预约自动转为「已停诊」并释放号源
- **日期边界** —— 不可预约已过去的日期；就诊当日之后不可取消
- **退号** —— 把号源加回去 + 置为 `cancelled`；管理端退号需登录并把操作人写进 `close_note`

> ⚠️ **「重复挂号拦截」已不在这个列表里** —— 它属于防黄牛范畴，2026-10-12 已连同
> `uq_appt_same_doctor` 唯一索引一起删除。现在**同一个人同一天可以把同一个医生的号重复挂满**。

## 并发安全

挂号是典型的「读-判断-写」：若不加锁，两个请求可能同时读到 `booked = total - 1`，然后都写入，造成**超卖**。

本项目的处理方式（**2026-10-13 起不再使用事务**）：

1. **条件 UPDATE，一条语句搞定** —— `UPDATE … WHERE id = $1 AND quota_booked < quota_total`。
   PostgreSQL 会给命中的行加锁，判断与扣减在同一步完成，中间没有空隙。
2. **只锁一行** —— 号源量就挂在排班行上，因此全程只需一把锁。原先「先排班、后时段」的两把锁及其加锁顺序问题随之消失，死锁面直接归零。
3. **数据库兜底** —— `CHECK (quota_booked <= quota_total)` 跨列约束，即使应用层出错也不会写坏数据。
4. **失败补偿** —— 写单失败就把号还回去；退号路由用 `AND status = 'active'` 保证重复退号不会重复还号。

并发实测结果（在**临时库**上跑，脚本见工作区 `.tmp/concurrency-test.js`）：

```
场景一：总号源 1 个，20 个请求同时抢   → 201 成功 1 个，409 号满 19 个
场景二：总号源 5 个，20 个请求同时抢   → 201 成功 5 个，409 号满 15 个
场景三：总号源 20 个，60 个请求同时抢  → 201 成功 20 个，409 号满 40 个

三次都满足：
  · 成功数 == 总号源，没有任何一次超卖
  · 库里的 quota_booked 正好等于成功数，且从不大于 quota_total
  · 成功的取号序号恰好是 1..N，不重复、不跳号
  · 每张挂号单号互不相同
```

> 复现方式：先 `PGDATABASE=临时库 node server/app.js --force`，
> 再 `PGDATABASE=临时库 PORT=3100 node server/app.js`，然后 `BASE=http://127.0.0.1:3100 node .tmp/concurrency-test.js`。
> **务必用临时库** —— 这个脚本会改号源总数。

## 架构说明

### 分层

```
浏览器
  └─ js/app.js 的第五节「跟后端打交道」   唯一的 fetch 出口：注入 Authorization 令牌，
                                          非 2xx 统一转成带中文提示的 Error
       └─ js/app.js 其余各节              页面逻辑：调用第五节的函数拿数据，往固定的 DOM 容器里填
            └─ Express 路由（server/app.js，需要登录的接口自己校验令牌）→ PostgreSQL
```

### 数据缓存策略

- **科室 / 医生**（5 + 10 条，几乎不变）在页面打开时一次性拉回来，存进 `js/app.js` 里的两个全局数组
  `departments` / `doctors`，并提供同步 getter：`deptName(id)` / `doctorName(id)` / `doctorTitle(id)` /
  `doctorFee(id)` / `doctorsOf(deptId)`。
  这样绝大多数渲染函数不必写成 `async`。
- **排班 / 挂号**（会变）按需异步拉取，每次都打接口。
- 字段名在 `server/app.js` 的映射函数里统一转成 camelCase，前端引用无需改写。
- **医院信息**不进缓存也不进数据库 —— 它是前端常量 `HOSPITAL`。

### 前端渲染模式

**页面骨架在 HTML 里，JS 只负责填内容。**

- 四个页面（`#page-home` / `#page-mine` / `#page-login` / `#page-admin`）和挂号向导的四个步骤
  （`#step1` ~ `#step4`）都是 `index.html` 里的静态标签，切换靠 `style.display`。
- JS 只在列表容器（`#deptList` / `#doctorList` / `#dateList` / `#periodList` / `#mineList` / `#adminBody`）
  里写 `innerHTML`。
- 事件不靠委托，而是直接写在标签上：`onclick="pickDept('D01')"`。所有函数都在全局作用域，所以标签里能直接调。

### 启动流程

`window.onload` 里三步：

1. 拉科室和医生（失败就 `alert` 提示「请确认后端已启动」，然后 return）；
2. 本地 `localStorage` 里如果存着令牌，问一次 `GET /api/auth/me` 确认还有效，无效就静默清掉；
3. `goHome()` 进首页，显示挂号向导第一步。

## 设计说明

**视觉风格** —— 朴素为主：白色卡片 + 浅灰背景（`#f5f6f8`），1px 边框，`border-radius: 4px`，
**没有渐变、没有阴影、没有动画**。主色是蓝色 `#2563eb`，只用在「确认挂号」这类主动作按钮上。
管理端表格用绿底标签标「待就诊」、灰底标「已取消 / 已停诊」。

**交互细节** —— 挂号流程靠标题文字（「选择就诊科室」→「选择接诊医生」→「选择就诊时间」）
加每步底部的「← 返回上一步」按钮定位当前位置；不可选项置灰并写明原因（「已约满」「无号」）；
破坏性操作（退号、停诊）走原生 `confirm()` 二次确认；结果用原生 `alert()` 反馈。

**响应式** —— 确认页的两栏布局在 700px 以下自动改成一栏；卡片网格用 `flex-wrap` 自动换行。

## 说明

- **挂号记录接口默认最多返回 500 条**（上限 2000）。建议用科室 / 日期筛选或搜索缩小范围，避免一次渲染过多 DOM。
- 科室、医生与患者数据均为**虚构示例**，不指向任何真实医疗机构。
- 后台账号密码为演示用默认值，**正式部署请立即修改**。
- 数据库密码写在 `server/app.js` 里（这是课程设计项目，本机演示用）。
  **真要放到公开仓库前，记得先把 `password` 换成环境变量或配置文件的读法。**
- `npm run db:reset` 会清空所有业务数据（含后台账号，会重新灌入默认账号），仅用于演示环境。
- 依赖只声明了 3 个：`express`、`pg`、`cors`。其中 **`cors` 实际没有被 `require` 过**
  （前后端同源，由 Express 一起发出去，不需要跨域头），属于历史遗留。
